# 按编排表选择 H.264 / H.265（2026-11-02）

## 配置规则

每路 `[stream] encoding` 是编解码选择入口。`h264` 对应 H.264 解码、标注编码和 RTP 输出；`h265` 对应 H.265 解码、标注编码和 RTP 输出。同一 TimeMux 组允许混用两种编码，解码后仍须满足该组的原始视频 caps 契约。

- 未写 `encoding` 时默认 `h264`；仅接受小写 `h264`、`h265`，其他值报 `STREAM_ENCODING_INVALID`。
- `[decode] depay/parse/decoder` 可省略，由编码自动补齐。显式配置不匹配时，报 `STREAM_DECODE_CODEC_MISMATCH`。
- H.264 允许 `rtph264depay / h264parse / v4l2h264dec`，也保留已有 `openh264dec` 分支；H.265 使用 `rtph265depay / h265parse / v4l2h265dec`。
- 通用 `[decode] colorimetry_override=bt709` 可按流用于 H.264/H.265，在 parser 后通过官方 capssetter 覆盖编码 caps 的色彩声明。旧 `h264_colorimetry_override=bt709` 作为 H.264 配置别名继续生效；在 H.265 使用旧键报 `STREAM_COLORIMETRY_CODEC_MISMATCH`，应改用通用键。两键值冲突报 `STREAM_COLORIMETRY_CONFLICT`，不支持的值报 `STREAM_COLORIMETRY_INVALID`。该处理不转换像素。

H.265 示例：

```ini
[stream]
camera_id=cam-001
source_type=rtsp
rtsp_url=<真实 H.265 RTSP 地址>
encoding=h265

[decode]
output_caps=video/x-raw,format=NV12
```

也可显式写出三件套：

```ini
[decode]
depay=rtph265depay
parse=h265parse
decoder=v4l2h265dec
output_caps=video/x-raw,format=NV12
```

只修改旧快照的 `encoding` 而保留显式 H.264 三件套会被拒绝，需要同时修改或省略三件套。

## 实现与部署

- 新增 `include/aibox/common/CodecProfile.hpp`，集中映射 codec、depay、parser、硬解码器、硬编码器、payloader 和编码 caps。
- Loader 校验并补齐解码配置，编码选择传入 `StreamInputPlan`；标注分支按每路编码选择编码器和 parser，在 RuntimeRegistry 保存每路输出 codec。
- AnnotatedRtspServer 按每路 codec 创建 appsrc caps、parser 和 RTP payloader；元件名 `src`、`pay0`、`enc_webrtc_<cam>` 等保持原有接口。
- 结构文本和执行计划 JSON 输出实际编码；TimeMux、demux 和模型算法不因编码选择改变。
- 165 的 `rtph265depay` 当前没有 `wait-for-keyframe` / `request-keyframe` 属性。默认关闭时不设置；若配置要求开启但元件不支持，明确报 `DEPAY_PROPERTY_UNSUPPORTED`。
- 拼图 `--record` 仍按原有 H.264 行为；H.265 软解兜底未在本次实施。

## 未通过项与验证边界

- 原 YOLO26 十二路 H.264 回归未通过：打开 `/dev/video32` 时返回 ENOMEM；对应内核日志明确记录 `msm_vidc_add_session: max limit 32 already running 32 sessions`。当时进程退出后没有视频设备持有者、iris_vpu refcnt 为0。不能据此认定是普通内存不足、内存泄漏，或已排除本次改动的影响。
- 确认无 pipeline、无视频设备持有者且模块引用为0后，通过 `tests/codec/recover_idle_vpu.sh` 重载 VPU 模块，随后四路 H.265/混合测试通过。十二路没有因此被标为恢复通过；用户后续明确仅能提供前四路编码切换，本次真实源验收按四路执行。

- 已验证的是板端 RTSP 输出编码与客户端实际解码；未将浏览器 WebRTC 播放 H.265、长期稳定性或模型精度列为已通过。


## 真实 H.265 流的额外兼容处理

四路源均为 HEVC Main、8 bit yuv420p、1920×1080、25fps。其中 cam-005 的色彩信息完整；cam-003、cam-004、cam-002 的 primaries/transfer 未声明，parser 输出 `colorimetry=2:4:0:0`，被 v4l2h265dec 拒绝，首次真实源启动未进入 PLAYING。

独立硬解验证中，在 h265parse 后使用 `capssetter caps=video/x-h265,colorimetry=bt709`，cam-003 成功输出30帧。因此将原 H.264 的声明覆盖能力改为按 CodecProfile 选择 `video/x-h264` 或 `video/x-h265`，复用一个配置和设置函数；TimeMux 和 batch 解码分支均接入该设置。旧 H.264 配置键继续兼容，不增加自定义预处理插件。真实 H.265 快照仅在内部 cam-002/003/004 启用通用覆盖项，cam-001 保留原声明。

这是已验证的硬解兼容措施，不证明实际源色彩规范就是 BT.709，也没有验收颜色分类精度。分类中的 None 或其他误判需与模型、输入数值和实际色彩规范另行评估。

真实流验收脚本为 `tests/codec/run_real_andon.py`，板端证据在开发目录 `output/codec_real_andon_20261102`。脚本逐路检查输入 HEVC，通过 `AIBOX_ANDON_SNAPSHOT` 调用现有 andon_start.sh；检查四路 HEVC 输出及抓帧、客户端重连、ROI 分类绑定、120秒短时观察，最后调用 andon_stop.sh 检查 NULL clean。最终结果以该脚本完成日志为准。
