# PPE YOLOX 零面积 ROI 导致 overlay 警告

- **现象**：切换到官方 `qtimlvconverter` 居中预处理后，四路推理运行时出现 `gst_util_fraction_multiply: assertion 'a_d != 0' failed`。调用栈定位到 `qtivoverlay` 计算 ROI 宽高比。
- **原因**：PPE 后处理已过滤浮点坐标下的无效框，但极小的正面积框经 `qtimetamux` 转换为整数像素 ROI 后，宽或高可能变成 0。此前没有在该转换边界过滤零面积 ROI，overlay 因而可能以 0 作为分母。
- **当前修复**：在 PPE pipeline 的 overlay 输入处，对可写 buffer 删除宽或高为 0 的 ROI metadata，视频继续通过；PPE 的类别、分数和 NMS 逻辑未改。板端修复后两轮四路运行和脚本启停通过，成功轮次未再出现该警告。
- **阈值影响**：此前模型后处理 `confidence_thresh=0.001`（0.1%，按 objectness × 最大类别概率筛选）属于评估候选下限，可能让更多低分、小尺寸候选进入后续链路。2026-11-02 默认显示阈值改为0.05；尚无证据证明每个零面积 ROI 都由低阈值造成，提高阈值也不能替代整数 ROI 校验。
- **后续深究**：采集零面积 ROI 对应的分数、浮点尺寸和裁剪前后坐标，统计不同阈值下的发生率，结合实际场景确定显示/业务阈值；确认 buffer 不可写时该过滤路径的行为。

# Andon 双模型串联嵌入的问题记录（2026-10-30～31）

本节只记录实际诊断到的问题和当前代码的明确限制。对应实现、模型契约和验收记录见 `Andon_YOLOX_MobileNetV2_4cam_Status.md`。

## 1. GLES converter 的 U16 mean/sigma 数值行为与一次线性变换不一致

- **现象**：分类输入使用官方 converter 的 GLES 后端配置 mean/sigma 后，与 BIN 所需 U16 编码不符。专项探针中，mean=0、sigma=0.5 的白色输入约为 16448，而不是按一次缩放得到的约 32768。
- **已确认的边界**：该板当前运行库不能直接沿用推导出的单次线性归一化参数。现象与重复数值变换一致，具体涉及的 SDK/GPU/CPU 执行路径仍需结合匹配版本源码深入确认，不能仅根据一个探针值断言所有版本的行为。
- **当前处理**：官方 converter 保留 ROI 裁剪、居中缩放、RGB 排列及 DMA 分配，mean/sigma 留空；现有 Builder 的 QNN sink probe 在同一可写 U16 缓冲区内完成 ImageNet 归一化和 QNN 量化编码，不新增预处理插件。
- **验证**：黑、白、红、绿、蓝五组输入的中心与黑色补边逐项检查通过。黑色编码为 `(0,1132,4318)`；白色中心为 `(60148,62623,65535)`。QNN 输出为 8 个有限 FLOAT32 logits。
- **后续深究**：定位该 SDK 版本的重复变换条件，确认其它 tensor dtype、RGB/BGR 排列和后端的差异；更换 SDK 或模型时重新执行输入探针，不能只检查尺寸。

## 2. 官方其它 converter 后端在 165 上未能替代 GLES

- **实际结果**：同一分类输入诊断中，OCV 后端出现段错误，FCV 后端初始化失败；因此未用于最终 pipeline。
- **当前状态**：最终采用 GLES 加现有代码的原位数值编码。上述诊断没有造成板端 SSH 断联。
- **后续深究**：保留对应运行库、插件版本和错误日志，定位后端实现、依赖和输入内存类型之间的关系。当前证据不足以认定 OCV/FCV 在所有模型或板卡上不可用。

## 3. batch=1 的 ROI non-cumulative 模式只处理首个灯具

- **现象**：初版串联链路检测到多个灯具，但终端只有首个 ROI 获得分类；只检查两个模型是否启动会漏掉这个问题。
- **原因**：官方 converter 在 non-cumulative 模式下将 ROI 数量限制到 batch 大小；当前分类模型 batch=1，因而仅输出首框。
- **当前修复**：第二级使用 `roi-batch-cumulative`，逐个处理同一帧的 ROI，保留 sequence-index、sequence-num-entries 和 parent-id，让第二级 metamux 合并同帧全部分类。第一级整图模式保持 non-cumulative。
- **验证**：零框、单框、多框测试通过；四个相机的终端 ROI 数与已绑定分类数一致，多框轮未出现 `ANDON_BINDING_ERROR`。零框时分类不执行，四路视频仍可抓帧。
- **后续深究**：在更高 ROI 数量、较慢分类模型和长时间运行下，测量整帧完成时延、队列占用和超时行为；不要在未验证时套用其它 batch 值。

## 4. Windows CRLF 标签触发官方 GstStructure 名称错误

- **现象**：初次灯具运行出现 `Invalid character '\r' ... Stacklight`，随后发生 GstStructure 创建、设置和序列化相关 CRITICAL。
- **原因**：标签末尾的 CR 字符进入官方后处理的标签名称，造成无效的 GstStructure 名称。
- **当前修复**：Andon 标签文件保存为 LF，修复后四路运行未再出现该错误。
- **后续深究**：决定在标签读取边界统一清理 CR/LF，还是在发布检查中拒绝 CRLF 标签；本轮未修改官方标签解析器。

## 5. 官方 mobilenet-softmax 的阈值单位不一致

- **代码事实**：`Configure` 把 settings 中的 confidence 除以 100；`Process` 把 Softmax 概率乘以 100，再直接与该阈值比较。例如配置 70 后，比较门限实际变为 0.7%，而不是通常期望的 70%。
- **当前影响**：当前配置 `confidence_thresh=0`、`results=1`，不依赖该阈值筛选，仍通过排序取得每个 ROI 的 Top-1；官方源码保持原样。
- **后续深究**：正式启用颜色置信度门限前统一单位，并补充确定性的边界用例；不能认为当前跑通验证已经验收了非零阈值行为。

## 6. 分类结果已绑定 ROI，但现有事件协议未表达独立颜色属性

- **当前事实**：官方 metadata、overlay 和 appsink 已按 parent-id 关联颜色；appsink 保存 classification_label / classification_confidence。
- **限制**：现有 `detection.frame` 的 Detection 只有 class_id、confidence、bbox 等字段，没有独立颜色分类属性。当前仍发送 Stacklight 检测类别和检测置信度，不把分类置信度覆盖到检测置信度。
- **后续深究**：在另行确定协议及规则消费方式后实现兼容输出，避免把画框 RGBA、检测类别和灯具颜色语义混用。此项是已接受的本轮范围限制，并非分类推理失败。

## 7. 后续替换 MobileNetV3 时存在模型 ID 触发条件

- **原有代码问题**：颜色 U16 数值适配及专用绑定统计通过 `model_id=mobilenet_v2_color_w8a16` 识别。正式使用新的 V3 model_id 时，不能只替换 BIN 路径而忽略这处判断。
- **2026-11-02 修复**：两处入口改按已有的 `preprocess=color_rgb_imagenet_quantized` 启用，原有128/RGB/U16/量化参数校验保留；切换真实V3 model_id后仍执行正确编码。零面积检测ROI过滤按后处理模块类型启用，不再绑定旧灯具模型ID。
- **后续约束**：每次换模型仍需核对 RGB/NHWC/128、训练归一化、输出 logits、类别顺序及新 BIN 的量化参数，禁止仅按“同系列”认定兼容。当前修复版V3的输入编码与旧V2相同；不是对任意V3输入规范的通用承诺。

## 9. 内存和 VPU 的观察范围

- **本轮结果**：多框轮采样 180 秒，后半段 RSS 为 629588～648324 KiB，末值相对该段起点增加 6092 KiB；测试中板端保持连接，各轮脚本停止均达到 NULL clean、VPU 引用 0。
- **证据边界**：有限时长观察不能证明长期无泄漏。没有实际 OOM、VPU 错误或对应时序证据时，不将单次 SSH 超时直接归因为 pipeline 内存泄漏。
- **后续深究**：在目标路数、ROI 上限、重连和多轮启停条件下长时间采集 RSS、DMA/CMA、队列深度与 VPU 会话状态。

# PPE 默认显示出现大量候选与重复 Human（2026-11-02）

- **现象**：用户运行 PPE 启动脚本后画面出现大量 Human、white clothes、white hat 框。实际日志四路平均每帧分别约39、25、43、32个框，说明框已经由后端输出，并非单纯前端叠加重复。
- **原因一**：数值对照/AP 评估用的 `confidence_thresh=0.001` 被保留到默认启动快照，没有单独设置实际显示下限。换算链路正确，实际门限就是0.1%。同场景单人样本有37个可见候选，30个低于1%；Human/帽子/衣服分数约78.6%/27.2%/10.5%。另一画面衣服分数约7.4%，因此不能仅为减少框数直接把统一门限提高到25%。
- **原因二**：只提高置信度到5%后，部分同一Human的重复框 IoU 约0.50～0.64，原 class-wise NMS 0.65不会抑制这些框；同类别的去重门限也需调整。
- **当前修复**：PPE 显示配置 `confidence_thresh=0.05`、`nms_iou_thresh=0.45`，让门限通过快照传到模块；新增启动参数日志及NMS边界测试。未配置NMS时模块默认仍为0.65，灯具配置和处理行为不变。
- **验证**：PPE解析、快照、NMS 0.45/0.65边界及灯具解析回归通过。实际单人 cam-004 的209帧中每帧 Human=1、衣服=1，186帧帽子=1，没有重复Human；四路视频抓帧和NATS分数检查通过。
- **边界**：当前仍是三个独立检测类别，不强制补齐“每人三个框”，也不把整帧 `results` 限为3。严格按每人绑定并限制帽/衣数量需要额外关联规则，不能仅凭置信度保证；本次没有实现该业务规则。当前阈值为给定场景的调试设置，生产门限仍需验证集与业务漏检/误检要求校准。

# 摄像头 caps 接入规则与后续代码精简（2026-11-02）

**讨论结论：可以减少、甚至取消“人工收集每种摄像头 caps 再逐个适配”的工作，但不能取消运行时 caps 检查。** 后续精简应围绕统一接入契约和明确的兼容规则进行；本节记录待实施方向，不代表已完成通用适配或删除现有机制。

## 本次已验证的问题及修复边界

- **现象与原因**：165 的 PPE 四路输入切换到 `192.168.50.41:8556` 后，源 `cam-003`、`cam-004`、`cam-002` 经 `h264parse` 输出 `colorimetry=0:4:0:0`，不被 `v4l2h264dec` 的动态 sink caps 接受，触发 `not-negotiated (-4)`，最终启动脚本报 `BOOT_DEAD`。错误发生在硬解码器之前，尚未到达 TimeMux。
- **当前处理与验证**：在这三路的 `h264parse` 与硬解码器之间加入官方 `capssetter`，通过 `[decode] h264_colorimetry_override=bt709` 按流启用。三路独立硬解各输出30帧；PPE 通过原启动脚本进入 `BOOT_OK / AGG_OK / READY_FOR_BROWSER`，四路均有检测聚合结果，四路标注 RTSP 均可解码，验收时未再出现协商错误。
- **能力边界**：`capssetter` 只覆盖格式声明，不转换像素，也不改写源 H.264 码流。当前验证证明链路可运行，尚未证明这些源的实际色彩规范就是 BT.709，也未评估覆盖声明对颜色及模型精度的影响。不得把所有摄像头无条件声明为 BT.709。

## 当前代码已有的机制

- **`strict` 模式**：`plugins/aiboxtimemux/gstaiboxtimemux.cpp` 使用首路输入 caps 作为协商基准，后续输入需要与其相交；色彩、帧率等差异仍可能造成拒绝。本次验收的0924 PPE快照使用该模式。
- **`canonical_raw` 模式**：使用配置的 `group_caps` 作为公共接入契约；`normalize_allowed_source_differences()` 在比较各路输入时移除 `colorimetry` 和 `framerate`，其余字段及 caps features 仍参与一致性检查。该机制是按规则接入，不要求为每种摄像头枚举完整 caps。
- **每路信息保留与恢复**：TimeMux 将输入 caps 引用保存到帧 metadata 的 `source_raw_caps`；`plugins/aiboxstreamdemux/gstaiboxstreamdemux.cpp` 的 `make_output_caps()` 据此恢复每路 colorimetry，并按配置设置输出帧率。该信息有实际消费者，不能因减少人工收集而直接删除。
- **公共输出**：`canonical_raw` 的输出由 `group_caps` 生成，并声明 `framerate=0/1`；这只是共享流的格式契约，不意味着已经完成逐路颜色转换。

## 后续精简方向与必须保留的检查

1. **解码入口兼容处理**：保留按流启用的色彩声明修正。后续研究能否根据实际输入、解码器能力及明确策略自动识别需处理的情况，减少人工配置；有效的不同色彩规范应通过经过验证的颜色转换处理，不能靠改声明冒充转换。
2. **统一 TimeMux 接入契约**：评估将适用的 pipeline 切换到已有 `canonical_raw`，用一套公共格式及允许差异的规则，替代持续扩大的摄像头 caps 白名单。切换前核对原始格式、尺寸、扫描方式、像素宽高比、其他字段和 caps features；明确哪些差异可忽略，哪些必须转换、分组或拒绝。
3. **保留运行时检查和诊断**：保留实际输入 caps、公共契约及拒绝原因的日志；保留分辨率、像素格式、位深、内存类型等兼容性检查。当前 caps 检查不能替代对真实 buffer 的 DMA、stride、offset 和布局检查；是否需要补充应根据实际接入失败证据确定。
4. **保留每路源信息**：继续维护 `source_raw_caps` 与 demux 的恢复链路。若未来所有输入已真实转换为同一色彩及格式，再结合消费者审查其精简空间。
5. **精简验收条件**：覆盖仅色彩/帧率不同的兼容输入，以及分辨率、格式、位深或内存条件不兼容的输入；前者应正确接入，后者应明确拒绝或经实际转换后接入。验证四路推理、demux、标注输出及脚本启停，并检查真实色彩差异对颜色分类的影响后，再删除被替代的适配分支。

官方组件说明：[GStreamer capssetter](https://gstreamer.freedesktop.org/documentation/debug/capssetter.html)。


## H.265 实流同样存在硬解前的色彩声明兼容问题（2026-11-02）

- **实际证据**：用户指定的 `8556/cam-003`、`cam-004`、`cam-002` 切为 HEVC Main 后，h265parse 输出 `colorimetry=2:4:0:0`，165 的 v4l2h265dec 拒绝该 caps，触发 not-negotiated。独立解码链在 parser 后覆盖声明为 bt709 后可输出30帧。
- **本轮实现**：统一使用 `[decode] colorimetry_override=bt709`，设置函数按 CodecProfile 选择 video/x-h264 或 video/x-h265，TimeMux 和 batch 解码分支共用；旧 h264_colorimetry_override 作为 H.264 配置别名保留。Andon 独立 H.265 快照仅在这三路启用，完整声明的 cam-005 不覆盖。
- **验证与精简关系**：真实四路 H.265 的双模型推理、HEVC 输出、抓帧、重连、120秒观察和脚本停止通过。该结果进一步说明，解码入口的声明兼容与 TimeMux 的原始视频接入契约需要分别处理，不能仅通过扩大 TimeMux caps 集合解决硬解前的拒绝。
- **边界**：覆盖声明不做颜色转换，也未证明源实际色彩就是 BT.709；模型颜色精度、自动识别兼容策略和长期稳定性仍需后续验证。完整记录见 `H264_H265_Switch_20261102.md`。
